# 設計案: レジスタ渡し（メモリ往復の削減）

状態: **段階 0 の測定の結果、中止（採用せず）**。結果は §6。対象版: 2.27.0。

## 1. 現状（測定）

JIT コードを `SPRINT_JIT_DUMP` で書き出して数えた、領域内の命令数とフレームのスロット（`(%r12)`）への書き込み・読み出し。

| ベンチ | 領域のバイト数 | スロットへの書き込み | スロットからの読み出し | callgrind 命令数 |
|---|---|---|---|---|
| oop | 4041 | 75（タグ13＋値62） | 60 | 696M |
| fib | 1359 | 14 | 10 | 2225M |
| closure | 1010 | 11 | 8 | 941M |
| loop | 666 | 9 | 7 | 4401M |

読み取れること:
- loop / closure / fib は、領域全体でもスロット操作が 10 前後で、これ以上削る余地は小さい。
- oop は、インライン展開した呼び出し（`p.add(d)`、コンストラクタ）の引数と戻り値がスロットに書かれ、さらに別のスロットへコピーされている（実コードで `mov 0x40(%r12)→0x50(%r12)` の形）。余地があるのはここ。
- fib は、インラインできない再帰呼び出しの引数渡しがフレーム経由（`ucall` の約束）。ここは別の設計になる。

注意: 2.21.0 のローカルのレジスタ写し（`lc_*`）は、命令数を減らしたが実時間は測れる範囲で変わらなかった。ストアは store-forwarding で安く、メモリ往復が律速とは限らない。

## 2. 方針の候補

### 候補 A: 遅延ストア＋出口の補償コード（本命）
いまは「メモリが常に正本（write-through）」なので、レジスタに値があってもスロットへ書く。これを「ガードが外れる出口のスタブで、レジスタからスロットへ書き戻す」に変える。
- 出口ごとに「その時点でレジスタにだけある値の一覧（レジスタ→スロット）」を持ち、出口の直前に書く小さなスタブを置く。
- 通常経路はストアなしで走る。特に、インライン展開した本体の引数・ローカルは、正常終了時には不要なので、ストアが完全に消える。
- コスト: 出口スタブの分だけコードが増える。出口の数は「ガードの数」に比例。
- 正しさの条件（MUST）: 出口に到達する全ての経路で、スタブが書く値と、インタプリタが期待するフレームが一致すること。`jit_finish` のフレーム連鎖（インライン本体・コンストラクタ）も、書き戻された値から組み立てられること。

### 候補 B: ループをまたぐレジスタ（C 項目）
`rbp` に固定できるローカルは 1 個だけ。これを複数にする（整数・浮動小数点のループ変数）。分岐の合流で、レジスタの割り当てを揃える必要がある。候補 A のスタブがあれば、出口側の問題は同じ仕組みで解ける。

### 候補 C: JIT 同士の呼び出しの引数をレジスタで渡す（fib 向け）
`ucall` の約束を変え、第1〜3引数をレジスタで渡す。再帰・インライン不可の呼び出しに効く。ただしフレーム（`Frame`）にローカルを置く約束と、例外・トレースの再構築があるため、A より変更が大きい。

## 3. 進め方（段階と中止条件）

0. 上限の見積もり実験（半日）: 安全でない実験ビルドで、インライン本体のスロットへのストアをすべて省き（出口の正しさは無視）、oop / closure の実時間を測る。**改善が 10% 未満なら、この計画全体を中止する**（メモリ往復が律速でないため）。
1. 候補 A の土台: 出口スタブの仕組みを、インライン本体の引数・ローカルだけに適用。ファザー（`jitfuzz_inline` / `jitfuzz_ctor`）で出口を強制して検証。
2. 候補 A をトップレベルのローカルへ拡張。
3. 候補 B。
4. 候補 C（必要なら）。

各段階のゲートは従来どおり（test、test-jit 3 モード、test-san、analyze、embed、os-test、fuzz、ファザー 7 本）に加え、出口を強制する新しいファザー（全ガードに摂動を入れる）を追加する。

## 4. リスク

- 正しさ: 出口で書き戻す値の取りこぼしは、サイレントな誤動作になる（ASan は JIT コードの中を見られない）。ファザーとテストが唯一の防御。
- 効果: 命令数は減っても、実時間が動かない可能性がある（候補 A の前に段階 0 で確認する理由）。
- 複雑さ: JIT のコード量が増える（出口スタブの生成・メモリ管理）。

## 5. 期待値（正直な見積もり）

- oop: 命令数で 10〜20% 減。実時間は 5〜10% の見込みだが、段階 0 で確かめるまで不明。
- closure / loop / fib: 小さい（スロット操作が元々少ない）。fib は候補 C が必要。
- 「LuaJIT 級」の目標に対する寄与は限定的。ボトルネックの本命は、別に挙げた文字列の表現（strcat）や型付き配列である可能性が高い。

## 6. 段階 0 の結果（2.27.0 で実施。実験コードは削除済み）

oop の 1 反復（命令 232）を、callgrind の命令単位の実行回数と JIT コードの逆アセンブルを突き合わせて数えた。

- 反復あたりに実行される JIT の命令: 209。うちフレームのスロット参照: 82（ストア 48、ロード・比較 33）。
- 理想的な上限: 読まれないストア 18、直前のストアから転送できるロード 29、後で読まれるストア 30。すべて省けても約 77 命令（約 33%）。
- 実時間の実測: ホットパス上で「読まれない」ストアのうち、安全と確認できた 16 個（全ストアの約 3 分の 1）を、複数バイトの NOP に置き換えた実験ビルドで、oop の時間は 48〜55ms → 46〜51ms。差はノイズ（±3ms）と同程度で、5% を超えない。
- 外せなかったもの: 「読まれない」と判定したストアのうち 1 個は、別の経路から読まれていて、外すと誤動作した。静的な「死んだストア」の判定は、出口とフレームの再構築を完全に考慮しないと危ない。

判断: 計画の中止条件（改善 10% 未満）に照らして、候補 A（遅延ストア＋出口スタブ）は、リスクと複雑さに見合わないとして採用しない。残りの上限（ロードの転送など）を足しても、実時間で 10〜15% を超える見込みは薄い。候補 B・C も、スロット参照が元々少ない loop / closure / fib への効果は小さいため見送る。

注意: NOP は命令スロットを消費するため、実際の削除より少し不利な測定になっている。ただし 16 個の削除で 5% 未満という結果は、全体の上限が小さいことを示している。

## 7. closure / oop の差を縮める検討（2.30.0 で実施。コード変更なし）

LuaJIT との差（closure 約4倍、oop 約7倍。起動の3msを除くと closure 0.85ns/反復 対 3.3ns、oop は約3ns 対 20ns）の内訳を測り直した。

| ベンチ | JIT領域の命令/反復 | 備考 |
|---|---|---|
| closure | 約47 | IPC が約4.5で、すでに実行幅に近い |
| oop | 約200（GC 約20、割り当てはインライン） | IPC 約3.3 |

oop の領域を逆アセンブルして分類すると、命令の約3割は、インライン呼び出しの引数・戻り値を16バイト単位で別のスロットへ写すコピー（受け手と引数を1スロットずつ上げて関数スロットを作る移動、戻り値の中継）。これらは出口でインタプリタのフレームを組み直すために必要で、消すには候補 A（出口で書き戻すスタブ）が要る。§6 の測定どおり、読まれないストアの3分の1を消しても5%未満だったので、全部消しても1割強が上限と見込まれる。

小さな案の見積もり（いずれも採用しない）:
- ステップ予算の減算の統合: ループの戻りとインライン呼び出しで1回ずつ減らす。まとめると予算切れで止まる位置が反復の途中でずれ、`--max-instr` の結果が変わる（§19 の決定性に反する）。
- 同じフィールドの繰り返し読みのガード省略: oop で1反復あたり約4命令（2%）。
- `% 定数` と GC の割り当て経路: すでに短く、1%未満。

LuaJIT との差の本体は、SSA 中間表現の上でのインライン化、ガードの外出し、アップバリュー・フィールドのレジスタ化、割り当て除去（allocation sinking）であり、いずれも「出口で値を書き戻す」仕組みを前提とする。この JIT（中間表現を持たない copy-and-patch）の延長では入らない。取り組むなら、ホットループ用の最適化層（別の中間表現と出口の再構築）を新設する規模の作業になる。
