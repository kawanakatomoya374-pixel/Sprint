# 統合 JIT（Copy-and-Patch 領域 JIT ＋ TraceJIT）の設計と現状

状態: フェーズ0 実装済み（TraceJIT は既定オン）。フェーズ1 以降は未実装。数値は 2026-11 の実測。

## 1. 役割分担（方針）

| 層 | 役割 | 現状 |
|---|---|---|
| インタプリタ（quickening 付き） | 冷たいコード、JIT 不採用のコード、deopt 後の再実行 | あり |
| **Copy-and-Patch 領域 JIT**（`jit.c`） | 対応範囲が広い土台。関数単位（unit）とループ単位。コンパイルが速い。**どのトレースも採用されなかったときの受け皿** | あり。fib/collatz/loop などで LuaJIT 並み |
| **TraceJIT**（`trace_ir.c` `jit_trace.c`） | 安定したホットループを、記録した実行経路で特殊化し、SSA 上で最適化（レジスタ保持・不要 store 除去・巻き上げ・allocation sinking）。**領域 JIT より速い場合だけ採用** | 既定オン。ただし採用される形が極端に狭い（§3） |

TraceJIT のバックエンドは領域 JIT と同じ stencil 表（`stencils.h`）で機械語を作る（`tr_*` atom）。つまり「Copy-and-Patch を土台に、トレースで最適化する」構成。

### 採用・降格ポリシー（不変条件）
1. **TraceJIT は領域 JIT より遅くならない**。`tools/bench/trace_cmp.sh` で全ベンチの on/off 比が 1.05 を超えたら不具合として扱う。
2. ループのルート記録は 1 回だけ（コンパイル成功でも拒否でも「確定済み」として再記録しない。`Proto.trace_settled` のビットセット）。
3. トレースが拒否・未対応なら、そのループは何も失わず領域 JIT に進む（`JIT_HOOK`）。
4. （フェーズ2）トレースの side exit が頻発するループは降格して領域 JIT に戻す（exit 率の計測で判断）。

## 2. フェーズ0（実装済み）で解決した問題

TraceJIT を既定オンにするために、まず「オンにしただけで遅くなる」原因を 4 つ潰した（`SPRINT_JIT_THRESHOLD=1e8` でインタプリタのみ測定、HEAD 比）。

| 問題 | 症状 | 対策 |
|---|---|---|
| 全命令に `trace_cap` 検査（`TRACE_STEP`） | インタプリタが 20〜55% 遅い（fib 0.43→0.52、minivm 0.14→0.22、tokenize 0.48→0.75） | インタプリタを **2 つの版にコンパイル**（`vm_loop.inc` を `RUN_LOOP_RECORDING` 0/1 で 2 回 include）。通常版には記録コードが無く、記録中だけバックエッジで記録版へ切り替える（`RS_SW_RECORD` / `RS_SW_NORMAL`）。`dt` ポインタ方式も試したが、レジスタ圧迫で minivm が +33% になり不採用 |
| `run_loop` 入場ごとに約 8KB を memset | コールバック（sort の比較関数等）が 2 倍遅い | 記録バッファの確保を最初のバックエッジまで遅延し、memset をやめた |
| 拒否したループを覚えていない | 毎反復「記録→拒否→版切替え」を繰り返す | `Proto.trace_settled`（ループヘッダのビットセット）。確定済みループは `proto_trace_blocked`（インライン数命令）で記録処理を呼ばない |
| 記録開始後にループが 2 周目へ戻らないと記録が終わらない | 記録版のまま走り続ける（命令の 18%） | ステップ上限（256）で記録を中止し、確定済みにして通常版へ戻す |

加えて、バックエッジごとの `jit_trace_site` 呼出しはトレースを 1 つも持たない関数では省略（`Proto.trace_any`）、`getenv` は初回のみ。

結果（既定設定、全ベンチ HEAD 比）: 全て ±7% のノイズ内（tokenize/fib は改善、他は同等）。`make test` `test-jit` `test-trace-jit` `test-san` `test-embed` `strict-clang` `analyze` が全て通る。

## 3. 測定で分かった TraceJIT の現状（フェーズ1以降の根拠）

1. **採用される形が玩具的**。`trace_build_ir` は「`while ローカル 比較 ローカル/定数` の形で、本体は LOAD_LOCAL/STORE_LOCAL/SMALLINT/CONST/ADD/SUB/MUL/NEG/DIV のみ、定数の型はループ条件の型と同じ」ループだけを通す。`for ... in range`、`%`、`//`、`if`、module 変数、配列、呼出しは全て拒否。fib/loop/collatz/nbody/sieve/matmul/tokenize の主ループは 1 つも採用されない（`SPRINT_TRACE_JIT_DEBUG=1` で `rejected` を確認）。
2. **採用されても速くない**。整数ループは領域 JIT と同等（0.319s 対 0.323s）。**float ループは 2 倍遅い**（2.10s 対 1.06s）。原因は f64 値を GPR に置き、演算ごとに `GPR→xmm0→演算→GPR` と往復するため（`ta_f64_binop`）。このため **f64 を含むトレースは現状採用しない**（`SPRINT_TRACE_JIT_F64=1` で解除。回帰テストは解除して実行）。
3. メモリ（load/store）・呼出し・割当てを表す IR 命令が無い。closure/oop が LuaJIT に及ばない根本原因（`trace-memory-v2.md`）。

結論: 現時点では TraceJIT は「安全に既定オンにできた基盤」であって、速度の利得はまだ無い。利得を出すにはフェーズ1〜3が必要。

## 4. 今後のフェーズ（バックエンド → ビルダーの順に修正）

フェーズ1の着手前調査で、**ビルダーだけ広げても速くならない**ことが分かった。バックエンドに次の欠落があるため、順序をバックエンド先行に改めた。

| 欠落 | 根拠 | 影響 |
|---|---|---|
| `IDIV` / `IMOD` を生成しない | `jit_trace.c:711` で `RETURN` と同じ「未対応」扱い | `%` `//` を含むループ（collatz、tokenize、loop）を通せない |
| ガードの出口が 1 種類 | 全 `GUARD_TRUE` が `TA_EXIT`（ループ条件偽の出口）へ飛ぶ | 本体内 `if` を「反復先頭へ戻して再実行」する deopt 出口で表せない |
| f64 を GPR に置く | `ta_f64_binop` が演算ごとに `GPR→xmm0→演算→GPR` | float ループが領域 JIT の 2 倍遅い（§3） |

### フェーズ1（バックエンド）
1. ✅ **実装済み** `IDIV` / `IMOD`: Sprint の床除算・床剰余の意味論で生成（2 のべき乗は `sar` / `and`、それ以外は `cqo; idiv` ＋符号補正、除数 0 と `INT64_MIN / -1` は deopt 出口）。
2. ✅ **実装済み** `GUARD_TRUE` の `imm` フラグで出口と極性を選べるようにする（`SP_TIR_GUARD_DEOPT` / `SP_TIR_GUARD_INVERT`）: 0 = ループ出口（従来）、1 = deopt（反復先頭の状態へ復元してヘッダからインタプリタで再実行）。スナップショットは既存の DEOPT 記述子を再利用。
3. ✅ **実装済み** f64 を XMM レジスタに割当て（`ta_alloc_regs` に XMM プール。PHI は固定割当て、exit stencil の FROM_IR 復元も XMM 対応）。完了後に f64 ゲート（§3）を外す。
   実装の要点: 除数が 0 / -1 なら deopt、2 のべき乗定数は `sar` / `and`（除算なし）、その他の小さな定数は逆数乗算（領域 JIT と同じ `jit_magic_of`）、変数除数は両オペランドが 32bit に収まる非負数なら 32bit `div`、それ以外は `idiv` ＋床補正。`rax`/`rdx` はプール末尾に置き、実際に使われたときだけ push/pop。実測（関数内ループ、Trace オン/オフ）: 定数 `%8`・`//4` のループ 0.39s 対 0.60〜0.68s（**1.6倍速**）、変数除数 0.75s 対 1.22s（**1.65倍速**）、`% 1000003` は 1.26s 対 1.15〜1.23s（同等）。
   併せて修正した不具合: 例外を捕捉した後、`cold.ev` が残るため版切替えの条件が偽になり続け、以降のループが一切記録されなかった。`cold` 状態を版の切替え時に丸ごと引き継ぐ方式に変え、切替えの条件自体をなくした（`RunCold`）。
4. 検証: 既存の IR 単体テスト（`trace_ir.c` 末尾の不変条件テスト）に IDIV/IMOD/新ガードを追加、`jitfuzz*.py` に生成パターンを追加。`trace_cmp.sh` で整数・float ループが領域 JIT 以上であること。

### フェーズ2（ビルダー）— 一部実装済み
✅ **実装済み**（`trace_build_ir_path`、従来の狭いビルダーが拒否したときに試す）: 記録済みステップ列を ocode 上で辿り、各条件分岐を「観測した方向」のガードにする。対象: ローカル、整数・float の定数と演算（同型どうし。`/` は float、`//` `%` は整数）、単項 `-`、比較＋条件分岐、前方 `JUMP` / `JUMP_IF_FALSE` / `JUMP_IF_TRUE`、`POP` / `DUP` / `DUP2`。反復の最初のガードがループを抜ける向きならループ出口、それ以外は deopt 出口（反復先頭の状態を復元してインタプリタで再実行。反復内の副作用はローカルの更新だけなので成立する）。最初の比較のオペランドは PHI か定数に限る（ループラベルとレジスタ固定の前提）。
✅ **降格ポリシー**: deopt を 16 回以上経験し、deopt あたりの平均反復数が 512 未満のトレースは無効化して領域 JIT に戻す（反復数は `vm->ileft` の減少量で測る）。導入前は偏りのない分岐（`if i % 2 == 0`）が領域 JIT の **23 倍遅かった**（3.1s 対 0.137s）が、降格後は同等（0.14s）。
✅ **検証**: `tests/cases/jit/jit_trace_branch.sp`（偏った分岐・途中で反転する分岐・collatz・forward jump・deopt 後のエラー）、`tools/jitfuzz_trace.py`（`make fuzz-trace`。800 本・4 構成で差分 0、トレース化は約 65%、うち約 25% が降格）。
✅ `for ... in range`（RANGE_NEXT。cur/stop/step を整数の loop-carried 値とし、刻みの符号と値は deopt ガードで固定、加算の溢れは deopt でインタプリタに任せる）。
✅ module 変数（`LOAD_MODULE`/`STORE_MODULE`。トレースはフレームのオペランドスタックの上の余白スロットに保持し、`jit_trace_site` が入口で `vm->slots` からコピー、出口で書き戻す。出口ラベルでは余白スロットへレジスタを格納する。スナップショットは変更せず、余白スロットに載る PHI は初期化時に読み飛ばす。ネイティブリンクと side trace はコピー処理を飛ばしてしまうので対象外）。測定: トップレベルの `s += i % 7` ループ（1億回）で Trace 0.19〜0.22s 対 領域 JIT 0.53〜0.56s（約 2.6 倍速）。
未実装:`and` / `or`（`JUMP_IF_*_OR_POP`）、float の反転ガード、int と float の混在演算、最初の比較がループ先頭でない形、内側ループ。

### フェーズ2b（配列の読み書き）— ✅ 実装済み（LICM は未実装）。着手前に見つけた落とし穴
Trace の deopt 出口は「反復の先頭状態を復元してインタプリタでその反復を最初から再実行する」ので、反復内に副作用が無いことを前提にしている。配列への書込み（`a[i] = v`）を入れるとこの前提が崩れる: 書込み後に deopt（`j += i` の溢れ、型ガード失敗など）すると、再実行で `a[i] = a[i] + 1` のような式が二重に適用される。したがって:

1. **書込みは反復の最後の deopt 可能点より後に移す（store sinking）**。ビルダーは `ASTORE` を IR に積むだけにして、バックエンドが「その反復の全ガード・溢れ検査が済んだ後」にまとめて出す。書込みと同じ配列への `ALOAD` が反復内で書込みより後にあるなら、順序が変わるので拒否する（保守的な別名判定）。書込む値・添字・配列ポインタは反復末尾まで生きるのでレジスタを消費する。
2. **IR**: `ALOAD(arr, idx)`（結果の型は記録時に観測した要素型、不一致・範囲外は deopt）、`ASTORE(arr, idx, value)`（第3オペランドは `aux`）。`ASTORE` は DCE で残す観測可能命令、検証・ダンプ・生存区間（`b` と `aux` の最終使用）を追加する。GC は非 moving の mark-sweep で書込みバリアは不要。
3. **ループ不変な読み出しの巻き上げ（LICM）**: ループラベルより前の命令は 1 回しか実行されないので、これが自然なプリヘッダになる。配列と添字がともにループ不変で、ループ内にその配列への `ASTORE` が無い `ALOAD`（matmul の `a[i]`）をラベル前に出し、結果のレジスタをループ中は固定（pinned）にする。
4. 配列ローカルは REF 型の PARAM として既に素通しできる（型ガード付き）。

実装結果: `ALOAD` / `ASTORE`、書込みの末尾への繰り延べ（全ての範囲検査の後に書く）、書込みの後の読出しの拒否、要素型は記録時の配列の先頭要素から決定。fuzz が見つけた 2 件の不具合を修正した: (1) `ASTORE` のオペランドの生存区間が後続の使用で短くなりレジスタが再利用された、(2) **最適化が、結果が未使用の失敗しうる命令（範囲外の読出し、溢れ、ゼロ除算）を削除してエラーを取りこぼしていた**（`IDIV`/`IMOD`/溢れ検査付き演算では以前から潜在していた）。失敗しうる命令は DCE で常に残す。
刻みの検査を入口専用ガード（`SP_TIR_GUARD_ENTRY`: ループラベルより前で 1 回だけ実行。刻みのスロットはメモリオペランドで直接比較）にし、カウンタの加算を定数の即値にした。測定（単一ループ、200万要素の配列を 50 回走査）: Trace 0.25s 対 領域 JIT 0.32s（約 1.25 倍速）、LuaJIT 0.16〜0.19s。入れ子のループでは外側を領域 JIT がコンパイルすると内側もそちらで走るため、Trace の効果は単一ループで見る。以前の測定: 1要素あたりの命令数は領域 JIT と同じ約20命令で、速度の利得はまだ無い（sieve/arr/matmul は Trace オン/オフで同等）。残る余分: 反復ごとの刻みガード（反復不変なので入口で 1 回で済む）、反復ごとの `items`/`len` の再読込み（トレース内に呼出しが無いので不変＝巻き上げ可能）、予算カウンタ、PHI の移動。
期待（未達）: sieve の内側ループ（`flags[j] = false; j += i`）は領域 JIT の約25命令から約10命令へ。matmul は行 `a[i]` の巻き上げで内側ループが半減。LuaJIT 比 2 倍前後の差の主因がここ。

### フェーズ3: メモリ・呼出し・割当て

## 5. 作業ルール
- 各フェーズで `make test` / `test-jit` / `test-trace-jit` / `test-san` / `test-embed` / `strict-clang` / `analyze` を全て通す。
- 利得は `tools/bench/trace_cmp.sh`（Trace オン/オフ）と `tools/bench/cmp.sh`（LuaJIT/V8/C 比較）の数値で示す。数値が出ないものは既定にしない。

### f64 の XMM 割り当て（実装メモ）
- `regs[v]` は GPR なら 0..15、f64 は `16 + n`（xmm n、プールは xmm2〜xmm15。xmm0/xmm1 と r10 はスクラッチ）。`ta_isx()` で判定する。
  配列・フィールド・フレームスロットとの境界は `movsd` を直接出す（`tr_sse_rr/loc/r10/base` の汎用スタンシル）。
- IR に `I2F` を追加。ビルダーは int と float の混在 `+ - * /` と int / int を `I2F` + float 演算にする（床除算・剰余は従来どおり拒否）。
- f64 を持つトレースが `NEWINST`（sink されないもの）や `LEAFCALL` を含むときは、C 呼び出しの前後で xmm を退避していないため従来どおり領域 JIT に任せる。
  `SPRINT_TRACE_JIT_F64=0` で f64 トレースを全面的に無効化できる（開発用）。
- 単純な float ループ（1 億回）: トレース 0.37s、領域 JIT 0.54s、LuaJIT 0.35s。

### 領域 JIT から内側ループのトレースを呼ぶ（bridge）
- 外側ループを領域 JIT でコンパイルするとき、内側にトレース済みのループがあれば、その**バックエッジ**に `htrace` スタンシルを置き、
  `jh_trace` → `jit_trace_site`（インタプリタのバックエッジと同じ入口状態）でトレースを走らせる。ループの出口まで走れば出口ラベルへ、
  ヘッダで止まれば（deopt／MISS で反復の先頭）ループ自身のネイティブコードがそのまま続き、それ以外ならフレームは設定済みなので領域を
  抜ける（`pc == UINT32_MAX` の特別な exit。`jit_finish` は何もしない）。
- 入口（ループへ落ちるところ）ではなくバックエッジに置く理由: ループ本体で宣言したローカルは入口では未初期化で、トレースの入口型ガードに合わない。
- 局所をレジスタに写すピン（`c->pin`）は bridge があると無効にする（トレースがローカルを書き換えるため）。
- トレースが領域より後にできた場合は `jit_region_trace_ready` が古い領域を退役させ（コードは残す）、次の訪問で作り直す。
- 以前の「内側ループがトレースで長く回るなら外側はインタプリタ」の規則は bridge 可能なとき適用しない。
- 外側ループ 1 回あたりのトレース入口コストは約 500 命令（`jit_trace_site` 215、`sp_jit_snapshot_restore` 160）。短い内側ループでは支配的で、次の改善点。
